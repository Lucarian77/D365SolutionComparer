# Phase 1 foundation contracts

This phase adds models, service contracts, a paged reader and tests. There is no membership UI, concrete membership reader/resolver/comparer, definition comparison, MembershipRequest or MembershipWorkAsyncFactory. Existing solution retrieval, comparison, UI, settings and exports are unchanged.

## Identities and snapshots

`EnvironmentIdentity` captures organization ID and a descriptive label. The label is not identity. Service clients and credentials do not belong in data models.

`SolutionIdentity` associates an environment with its local solution GUID and unmodified Unique Name. It is separate from the currently grid-bound `SolutionInfo`, preventing new autogenerated columns. Local solution IDs are for retrieval; existing solution matching still uses Unique Name.

`SolutionComponentRecord` retains solutioncomponent ID, numeric component type, object ID, inclusion behavior, root record ID and metadata flag. Unknown numeric values and nullable fields are preserved. The enclosing solution snapshot supplies solution/environment provenance.

`ComponentIdentity` pairs a raw record with Resolved, Unresolved, Unsupported or Ambiguous status. Only Resolved can carry a trusted key. Keys must be scoped by component type and required parent identity; a future resolver defines normalization per type. Do not infer identity from display name or assume every GUID is portable across environments.

`MembershipSnapshot` is immutable and copies its component collection. Its state is one of:

- Complete: a present solution was fully read, including a successful zero-component read. Identity resolution can still be incomplete.
- SolutionAbsent: the selected solution was positively established as absent; no fabricated solution GUID is required.
- Unavailable: retrieval could not establish an inventory; a diagnostic is required.

The retrieval interface reads a known-present solution and returns raw records wrapped in Unresolved identities. A resolver processes the records; the future orchestrator constructs an enriched snapshot from its outputs. Cancellation and retrieval failures propagate. The orchestrator may represent an unavailable side but must not turn it into a successful empty inventory.

## Presence and one-sided comparisons

`MembershipCompareResult` separates presence from identity resolution. Presence is Indeterminate, PresentInBoth, OnlyInSource or OnlyInTarget. Inclusion fields remain available on the raw source/target records; shared presence does not mean equal inclusion behavior or definitions.

The result constructor rejects a one-sided classification unless the present identity is Resolved, the opposite component is null, and explicit absence evidence is supplied. Unsupported, Unresolved and Ambiguous identities can only be represented as Indeterminate, even if the opposite solution is absent. It also rejects shared presence with unresolved or different-type identities.

The future comparison implementation is responsible for validating keys and evidence against its actual snapshots. The result model does not perform matching or certify a caller-supplied evidence enum.

| Situation | Required future behavior |
| --- | --- |
| Resolved identity paired with a matching resolved identity of the same type | PresentInBoth; definition equality remains unknown |
| Resolved source member, target solution positively absent | OnlyInSource with OppositeSolutionAbsent evidence |
| Resolved target member, source solution positively absent | OnlyInTarget with OppositeSolutionAbsent evidence |
| Unmatched resolved member, opposite relevant inventory completely and unambiguously resolved | One-sided result with CompleteResolvedInventory evidence |
| Opposite inventory unavailable, incomplete, or containing identities that could conceal a match | Indeterminate; failure to resolve is not proof of absence |
| Unsupported/unresolved/ambiguous member | Retain the record as Indeterminate |
| Duplicate candidate keys | Ambiguous; never take the first record |
| Both solutions absent | No component rows; retain both solution-level states |

`ISolutionMembershipComparer` requires snapshots for the same Unique Name using OrdinalIgnoreCase, including explicit absent sides. These are contracts, not a shipped comparison engine.

## Paged retrieval

`DataversePagedReader.ReadAll` accepts an `IOrganizationService` through its constructor and a `QueryExpression`, root primary-key logical name, cancellation token, progress callback and optional page size (1 through 5000).

- Deep-clones the query with the SDK data contract so the caller's filters, columns, orders and page settings are not mutated.
- Starts at page one and appends root primary-key ascending order as a deterministic tie-breaker after existing ordering.
- Caller must supply the actual primary-key logical name for the queried standard table, initially `solutioncomponentid` for `solutioncomponent`.
- Uses `MoreRecords` and the returned cookie unchanged. A short page is not treated as the end.
- Deliberately rejects TopCount, distinct and joined queries. Joined results can duplicate root IDs and invalidate the ordering guarantee.
- If more rows are indicated without a cookie, fails explicitly rather than falling back to simple paging's limitations.
- Fails on null responses, repeated cookies, or empty pages claiming more records.
- Checks cancellation before and after SDK calls and after progress callbacks. An in-flight synchronous SDK request is not forcibly interrupted.
- Reports cumulative page/record counts on the calling thread. Progress is not a completed inventory; no partial collection is returned after faults, callback exceptions or cancellation.
- Does not add retries, parallel SDK calls, metadata requests, or environment-wide caching.

Deterministic paging is not a transactional snapshot: concurrent server changes can still affect a multi-request read. Captured timestamps expose when retrieval occurred.

Microsoft documents paging cookies, ordering requirements and simple paging limitations in [Page results using QueryExpression](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/org-service/queryexpression/page-results). Raw member attributes are described in the [solutioncomponent reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/solutioncomponent).

## Future WinForms integration

Invoke membership retrieval from XrmToolBox `WorkAsync` using `WorkAsyncInfo.Work`, `ProgressChanged`, `PostWorkCallBack` and `IsCancelable`. These APIs were verified in the installed baseline Extensibility assembly. Bridge cancellation into the reader; marshal progress to UI callbacks. Capture environment identities and a request generation, then reject completions after connection changes, selection changes or disposal. Do not infer freshness from a display label. No adapter or existing-control wiring is added now.

## Test and package boundaries

The test project is a traditional .NET Framework 4.8 C# library with C# 7.3, a one-way project reference to the plugin, and private MSTest.TestFramework/TestAdapter 2.2.10 references. It uses no UI automation or live Dataverse dependency. A small fake IOrganizationService supports paging tests. The plugin has no test-package references and the unchanged nuspec lists only production DLLs and existing assets.

Build/run instructions and results are in [Validation.md](Validation.md).
